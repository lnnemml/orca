# 019 — `orca_2json` geometry post-condition failed a plain `Opt` with a misleading Bohr→Å message

**Status:** solved (Phase 4.5 Stage E1c). **Area:** `src-tauri/src/parse/mo.rs`,
`src-tauri/src/results.rs`. **Kind:** false-positive post-condition + a fatal branch that
should have been non-fatal.

## Symptom

Re-parsing the first **displaced-endpoint plain-`Opt`** jobs (the MeNH₂+EtI forward/backward
geometries generated by the E2 endpoint feature — `! Opt`, **no `Freq`**) failed the WHOLE
results parse with a banner reading roughly:

```
orca_2json: geometry post-condition failed: max Δ 0.027 Å exceeds 1e-4
            (a missed Bohr→Å conversion looks like ≈1.889×)
```

The message is a **red herring** — twice over. First, 0.027 Å is **not** a unit error: a missed
Bohr→Å conversion scales interatomic distances by ≈1.889×, i.e. metre-scale disagreement, not
0.027 Å. Second, and worse, an MO-pipeline problem took down the *entire* parse: energy,
geometry, thermochemistry, and charges — all of which parsed fine — never reached the screen.

## Root cause

Two independent defects, both surfaced for the first time by these jobs (the first plain-`Opt`
jobs that also had MO parsing — every earlier MO job was Opt+Freq, a scan, or an SP):

1. **`orca_2json`'s geometry lags the property-final geometry on a plain `Opt`.** `Atoms.Coords`
   in the JSON come from the `.gbw`, which stores the wavefunction of the **last SCF** — not
   necessarily the last *reported* geometry. On **Opt+Freq**, Freq re-solves the wavefunction at
   the exact final geometry, so the `.gbw` geometry == the property-final geometry byte-for-byte
   (max Δ < 1e-4 Å — the fast path). On a **plain `Opt`** the wavefunction is one opt-step behind
   the final reported geometry: measured **0.027 Å** on the real MeNH₂+EtI jobs. `mo.rs`'s
   post-condition asserted `max Δ < 1e-4 Å` and returned `GeometryMismatch` — so this benign,
   **same-unit** lag failed the check with a message that blamed a unit conversion.

2. **The MO branch was fatal.** `results.rs` returned `ParseOutcome::ParseFailed(...)` for any MO
   error (converter spawn *or* geometry verify). "No MO data is a normal state" (unit 3.7 — xTB
   gbw already produces `Ok(None)`), so an MO problem must never abort the parse of everything
   else.

## Fix

**`mo.rs` — a three-way ratio classifier (`classify_geometry`, pure, unit-tested)** replacing the
single 1e-4 threshold. Distance-matrix based (translation/rotation invariant):

1. `max Δ < 1e-4` → **pass** (fast path — Opt+Freq / scan; unchanged, no regression).
2. else the **median distance ratio** `r = median(dist_json / dist_ref)` over pairs with
   `dist_ref > 0.9 Å` (skip tiny distances = division noise). `r` within ±8% of **1.889** *or*
   **0.529** → `GeometryUnitError { ratio }` — an honest, loud Bohr↔Å miss, **either direction**.
3. else if `max Δ < 0.5 Å` **and** `r ≈ 1` (±8%) → **pass** — benign same-unit `.gbw` staleness.
4. else → `GeometryMismatch { max_delta }` — a genuinely different structure, **not** a unit error.

The three ratio bands never overlap: `0.529±0.042 = [0.487, 0.571]`, `1.0±0.08 = [0.92, 1.08]`,
`1.889±0.151 = [1.738, 2.04]`. A real unit error in either direction is still caught; only a
same-unit lag (`r ≈ 1`) passes. New `ParseError::GeometryUnitError { ratio }` carries the honest
Bohr↔Å diagnostic; `GeometryMismatch`'s message was neutralised (no Bohr→Å claim) because it is
**shared** by four threshold-only readers (`property`/`hess`/`xyz`/`relaxscan`) for which the
neutral wording is also correct — they were left otherwise untouched and still fail loudly on a
real Bohr→Å via `GeometryMismatch`.

**`results.rs` — the MO pipeline is now non-fatal.** Both `return ParseOutcome::ParseFailed(...)`
in the orbitals branch became `eprintln!("orca_2json (no orbitals): {e}")` + `orbitals = None`.
(`eprintln!` matches the crate's warning convention — there is no `log`/`tracing` dependency.)
Energy/geometry/thermo/charges/frequencies still parse and display; only orbitals may be absent.
With the Part-A fix these jobs now show orbitals too — Part B is the defense-in-depth backstop
for any *future* MO failure.

## Bite (negative controls, `parse/mo/tests.rs`)

- `unit_error_caught` — json = ref × 1.889 → `UnitError`. **Bite:** the old single-threshold code
  called this `GeometryMismatch`, conflating a unit error with any over-tolerance mismatch.
- `staleness_passes` — ref perturbed ~0.03 Å (same unit) → **pass**. **Bite:** the old 1e-4
  threshold *fails* here — this is exactly the false `ParseFailed` the unit fixes.
- `real_mismatch_fails` — same unit, one pair off ~1 Å, `r ≈ 1` → `GeometryMismatch` (not
  `UnitError`, not pass).
- `fast_path_still_passes` / updated `missed_conversion_fails_loudly` (real fixture, Bohr
  magnitude → `GeometryUnitError`).

## Why it was never hit before

Every prior MO job was Opt+Freq (byte-identical geometry → fast path), a scan (routed
profile-only, `debugging/015`), or an SP (single geometry). The displaced-endpoint plain-`Opt`
jobs are the **first** plain-`Opt` jobs with MO parsing, so the `.gbw`-lags-final gap had never
been exercised.
